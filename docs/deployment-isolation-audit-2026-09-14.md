# 맥미니 네트워크 경계 검증과 런타임 보완

2026-09-14, 사용자의 백엔드·홈서버 작업 위임에 따른 검증이다. 운영 앱·Laravel·Redis·Tunnel을 재시작하거나 교체하지 않았다. 새로운 공개 접근 정책도 적용하지 않았다.

## 현재 운영본에서 확인한 위험

운영 백엔드는 여전히 `conan-be:472aff7`이며 UID 0, 추가 capability 제한 없음, NoNewPrivileges 설정 없음, PID 상한 없음, CPU 2·RAM 3 GiB다. 전용 모델 볼륨만 마운트하고 호스트에 포트를 게시하지 않은 상태는 유지된다.

운영 컨테이너에서 이미 확인한 세 대상에 각각 1초짜리 TCP 연결 후 즉시 닫는 시험을 했다. 애플리케이션 명령·로그인·데이터 조회나 포트 범위 스캔은 하지 않았다.

| 대상 | 운영 백엔드에서 TCP 연결 | 의미 |
| --- | --- | --- |
| Laravel의 확인된 내부 주소, 80 | 성공 | 다른 Compose 네트워크에 두어도 현재 내부 접근이 가능함 |
| Redis의 확인된 내부 주소, 6379 | 성공 | Redis 인증·데이터 접근 여부를 시험한 것은 아님 |
| 맥미니 Tailscale 주소, 22 | 성공 | SSH 로그인 성공을 뜻하지 않지만 호스트 관리 포트까지 도달함 |

따라서 현재 네트워크 구성을 그대로 둔 채 이메일 Access를 제거하지 않는다. 기존 서비스의 실행·인증 상태를 격리 증거로 사용하지 않는다.

## 운영과 분리한 검증 결과

이름에 `chamsae-isolation-check` 또는 `chamsae-egress-check`를 붙인 일회용 네트워크·컨테이너를 별도로 만들었다. 테스트 컨테이너에는 사용자 파일·운영 볼륨·API 키·Docker socket을 전달하지 않았다. 종료 후 해당 테스트 컨테이너와 네트워크만 정리했다.

1. `internal` 네트워크 하나에만 연결한 비특권 테스트 컨테이너에서 위 세 대상과 공용 HTTPS 주소로 직접 연결이 모두 실패했다.
2. 내부망과 별도 외부망에 연결한 Squid 출구를 두고, 테스트 앱은 내부망 하나에만 연결했다. 요청은 출구를 통해서만 전달했다.
3. 허용된 NAVER API의 TLS 연결 후 HTTP 400 응답을 받았다. 키 없이 보낸 요청이므로 검색 성공·품질·비용 시험이 아니다.
4. 미허용 도메인과 사설 IP 직접 지정은 프록시 403으로 거절했다.
5. **허용 도메인 `api.deepseek.com`을 테스트 프록시 안에서 사설 IP로 해석하도록 고정**한 경우에도 403으로 거절했다. 허용 이름만 확인하고 사설 목적지로 연결하는 경로를 검사했다. 실제 DNS rebinding 공격의 모든 시간적 변형을 검증한 것은 아니다.

첫 프록시 시험에서는 NAVER 루트 URL의 리다이렉트를 따라가 DNS 오류와 섞였다. 최종 시험은 리다이렉트를 따르지 않고 API 경로를 사용해 원본 응답과 프록시 거절을 구분했다. 내부 프록시 이름도 최종 시험에서 정상 해석됐다.

재현 스크립트는 [verify_egress.py](../scripts/verify_egress.py), 빌드·설정은 [egress](../deploy/egress/README.md)에 있다. 최종 시험 이미지 ID는 `sha256:774e9e9097e16c3f116b10e8d80fab2e039d2f3fc891d9e401e7b5f572af6916`다. 로컬 테스트 태그이며 운영용 서명 이미지로 취급하지 않는다. 서버에 검증 디렉터리와 테스트 이미지는 남겼고 실행 중 테스트 컨테이너·네트워크는 없다.

## 비특권 런타임 CI

BE `ddbfa55`의 [ARM64 CI](https://github.com/Dynamic-Juo/be/actions/runs/34857498782)가 성공했다. 앱을 UID/GID 10001로 실행하고 앱 코드와 쓰기 디렉터리를 분리했다. CD Compose에 PID 128, `/tmp` tmpfs 768 MiB·nosuid/nodev/noexec를 추가하고 기존 cap_drop ALL·no-new-privileges를 유지한다.

CI의 외부 통신 없는 회귀는 731 passed, 2 skipped, 2 warnings이며 gateway 6개도 통과했다. 별도 제한된 실행에서 실제 번들 얼굴 모델 초기화와 모델 캐시·접수 상태·결과 디렉터리 쓰기가 성공했다. 전체 STT·분류기 모델 다운로드·실영상·재시작 결과 복원과 운영 피크 메모리는 이 검증에 포함하지 않는다.

캐시 경로는 `/root/.cache`에서 `/home/app/.cache`로 변경됐다. 기존 root 소유 볼륨을 그대로 마운트하면 쓰기 실패가 가능하므로 신규 배포 전 볼륨의 경로·소유권·복원과 롤백을 검증해야 한다. 운영 볼륨은 이번에 변경하지 않았다.

## 아직 공개할 수 없는 조건

- 검증한 내부 네트워크·출구와 서비스 전용 Tunnel을 실제 운영 구성으로 연결해야 한다. 공유 cloudflared를 안전한 경계로 가정하지 않는다.
- 출구 프록시는 외부 연결 권한을 갖는 별도 신뢰 대상이다. 프록시 취약점·같은 OrbStack 커널 침해까지 이 시험이 막았다고 주장하지 않는다. 더 강한 경계는 독립 VM/외부 서버로 분리한다.
- 실제 YouTube·HF·DeepSeek·NAVER 사용 경로가 허용 목록을 통해 작동하는지 검수해야 한다. 라이브러리가 프록시를 무시하면 직접 연결이 실패하도록 내부망만 사용한다. 실패를 이유로 일반 외부망을 앱에 다시 연결하지 않는다.
- 실행 중인 STT·다운로드의 강제 종료, 요청별 메모리·임시 파일 회수, 지속 상태와 안전한 최초 배포 전환은 아직 완료되지 않았다.
- 프론트·Vercel 변경은 팀장 담당이다. 이 작업에서는 원격 프론트 코드와 Vercel 설정을 변경하지 않는다. 필요한 계약·검수 항목은 BE 문서로 전달한다.
